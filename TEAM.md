### Work division

Explain how the team will assign, review, and complete work.

Work Assignment: The Project Manager will coordinate task allocation based on each member's role, skills, and availability. Every task must have a clear description, an assigned owner, an agreed deadline, and expected deliverables. Tasks will be tracked using GitHub Issues or another team-approved method.

Work Review: Members will submit completed work for review through GitHub pull requests or the agreed submission channel. The assigned reviewer will check the work for accuracy, quality, completeness, and compliance with project requirements. UI/UX designs will be reviewed for usability and consistency, while code will be checked for functionality and testing. Feedback must be addressed before approval.

Work Completion: A task will be considered complete only when its deliverables have been submitted, reviewed, and approved, and any required corrections have been made. Approved code or documentation will be merged into the appropriate branch, and the task status will be updated. Members must communicate delays early and provide progress updates to help the team meet its deadlines.

General rule: Every member is responsible for completing assigned tasks on time, maintaining clear documentation, responding to feedback, and ensuring that their contributions meet the team's agreed standards. The team will monitor progress regularly and address outstanding tasks promptly to prevent delays to the overall project.

Tasks will be assigned according to each member's role, skills,
availability, and the project's requirements.

Each member is responsible for completing their assigned work and
providing progress updates when necessary.

### Version control rules

Explain branch naming, commit message rules, PR rules, and merge rules.

Branch Naming Rules
Use the format type/short-description.
Use lowercase letters and hyphens.
Recommended prefixes are feat/, fix/, design/, docs/, test/, refactor/, and chore/.
Examples: design/school-dashboard, feat/parent-login, and docs/update-team-agreement.
Create a separate branch for each major task or feature.
Do not work directly on main unless an exception has been agreed upon by the team.

Commit Message Rules
Use the format type: short description.
Examples: feat: add parent login, design: add dashboard wireframes, and docs: update TEAM.md.
Keep messages clear, concise, and specific.
Commit related changes together and avoid mixing unrelated work.
Do not commit passwords, API secrets, or confidential information.

Pull Request Rules
Submit completed work through a pull request targeting main.
Each PR must have a clear title, description, and relevant evidence.
Link the related GitHub Issue where applicable.
Include screenshots for interface changes and test results for development changes.
Request at least one review from another team member.
Address review comments before merging.
PR authors should not approve their own changes.

Merge Rules
Merge only after the required review and approval.
Resolve merge conflicts and outstanding review discussions before merging.
Development changes must pass the agreed tests before merging.
Keep main stable and ready for integration and demonstration.
Use Squash and merge as the default method unless the team agrees otherwise.
Delete temporary branches after successful merging when they are no longer needed.
Communicate significant changes that affect other team members.
The Repository Manager should coordinate merge conflicts and help maintain repository consistency.

Accountability
Every member is responsible for following these rules, keeping their work organized, and communicating problems early. Exceptions should be discussed with the team and documented where necessary.
- The main branch should contain reviewed and stable work.
- Members should work on appropriate feature branches when necessary.
- Commit messages should clearly describe the changes made.
- Changes should be reviewed before being merged into the main branch.
- Unrelated changes should not be included in the same commit where
  practical.
- Team members should avoid overwriting another member's work without
  discussion.
- Important project documents, including design notes, user flows,
  requirements, and testing records, should be maintained in the
  appropriate repository folders.
  
### Academic integrity and AI rules

Explain how the team will prevent freeloading, plagiarism, dishonest AI use, and unexplained work.

AI tools may be used to support research, brainstorming, documentation,
design exploration, and development where appropriate.

Preventing freeloading: Each team member will be assigned specific tasks with clear deadlines and expected deliverables. Progress will be monitored through GitHub Issues, commits, pull requests, meeting updates, and submitted work. Members who consistently fail to contribute will be contacted and held accountable.

Preventing plagiarism: All members must produce original work, acknowledge external sources, and provide proper citations where necessary. Submitted work will be reviewed for copied content, and any suspected plagiarism will be investigated before appropriate action is taken.

Preventing dishonest AI use: AI tools may be used to support research, design, documentation, and development, but members must review, understand, and verify their outputs. No member should present AI-generated content as independently completed work when disclosure is required, submit fabricated information, or use AI to misrepresent their contribution. All AI use must comply with the university's academic integrity requirements.

Preventing unexplained work: Every contribution must have a clear purpose and relate to an assigned task or approved project requirement. Members should document significant decisions, explain their changes in commit messages and pull requests, and provide supporting evidence where necessary. Work that cannot be adequately explained or verified will be returned for clarification and review before acceptance.

General rule: Every member is responsible for ensuring that their contributions are original, verifiable, relevant to the project, and completed honestly. Concerns will be documented and addressed fairly, with serious or repeated violations escalated to the lecturer when necessary.

However, team members must review, understand, and verify AI-generated
content before using it in the project.

AI-generated code must be tested, and AI-generated information must be
checked for accuracy.

Members should not submit fabricated research findings, invented client
requirements, or unverified information as factual evidence.

All work must comply with the university's academic integrity
requirements and the project's agreed standards.

### Conflict resolution

Explain what happens if a member fails to attend, fails to contribute, submits dishonest work, or blocks progress.

Failure to attend: Members who miss scheduled meetings without prior notice or a valid reason will be contacted by the Project Manager to explain their absence. Repeated unexplained absences will be documented and discussed with the team for appropriate action.

Failure to contribute: Members who consistently fail to complete assigned tasks or provide meaningful contributions will be reminded of their responsibilities and given a reasonable deadline to improve. If the problem continues, the team may redistribute their outstanding tasks and escalate the matter to the lecturer where necessary.

Dishonest work: Members must not submit fabricated information, plagiarised content, false progress reports, or work they claim to have completed when they have not. Any suspected dishonesty will be reviewed fairly, and the member will be asked to explain their actions. Confirmed cases will be documented and referred to the lecturer in accordance with the university's academic integrity policies.

Blocking progress: Members must communicate promptly, cooperate with others, and avoid deliberately withholding information, files, approvals, or access needed for the project. If a member's actions delay progress, the Project Manager will first attempt to resolve the issue through discussion. If the obstruction continues, the team may reassign affected tasks, document the incident, and escalate the matter to the lecturer.

General rule: All concerns must be handled fairly, consistently, and based on evidence. Members should be given an opportunity to explain their circumstances and correct their behaviour. Repeated or serious violations may result in further action in consultation with the lecturer.
Team members should address disagreements respectfully and focus on
finding solutions rather than assigning blame.

If a member is unable to complete a task, they should inform the team
as early as possible so that alternative arrangements can be made.

If a deadline is missed without prior communication, the Project Manager
should discuss the situation with the member and agree on corrective
action.

Repeated problems should be brought to the team's attention and
resolved fairly.

Every member should be accountable for their assigned responsibilities
and should acknowledge the contributions of other team members.
